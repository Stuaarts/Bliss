# REST response diagnostics (#15)

Matched REST requests emit one INFO event through `com.bliss.http.requests` when
the existing response filter prepares their response. The default packaged
production profile wraps the event in Quarkus JSON console output; local/dev/test
retain text console output. The message has this bounded field set:

```text
event=rest_response requestId=<server UUID> method=GET operation=CatalogResource.categories status=200 durationMs=2
```

The request ID is generated by the server and returned in `X-Request-ID`. Mapped
problem responses use the same ID. Client-supplied request IDs are ignored.
Operation names come from the matched resource class and Java method, such as
`CatalogResource.offering`, rather than a raw URI or resource ID. Standard HTTP
methods are allowlisted; other methods become `OTHER`. If resource metadata is
unavailable, the operation is `unmatched`. Renaming a resource/method changes this
operation name and must be considered when configuring future dashboards.

`durationMs` is a monotonic elapsed measurement from the matched REST request
filter to its response filter, rounded down to milliseconds. It excludes earlier
routing/authentication, response entity serialization, network delivery and client
work. It is not an end-to-end latency or response-delivery acknowledgement.
Request properties carry timing/correlation; no thread-local MDC state is added.

This is a REST diagnostic, not a universal HTTP access log. Management endpoints,
authentication failures before REST filters, routing failures before a match,
transport disconnects and background workflow execution are outside its coverage.
Existing HTTP metrics and [management probes](MANAGEMENT_ACCESS.md) remain separate.
There is no distributed trace or automatic propagation across workflow waits,
scheduled dispatch and process restart.

## Content and error boundaries

The response event reads no request/response bodies, authorization/cookie headers,
query strings, raw paths, actor identities or business resource IDs. Its request
ID is diagnostic metadata, not authorization and not a metric label. Do not add
private messages, dispute evidence or user-supplied correlation values to it.

Mapped server failures emit an ERROR event through `com.bliss.common.api.ApiErrors`:

```text
event=api_failure requestId=<same server UUID> exceptionType=java.lang.IllegalStateException
```

This mapper omits exception messages, nested causes and attached throwables, which
could carry submitted content or database details. The HTTP response remains the
same generic problem response. Operators can correlate the error type and response
event with the request ID; full exception/stack diagnostics require a restricted
investigation procedure with its own content/access review. This reduces detail in
the routine mapped-error log.

`quarkus.flow.tracing.enabled=false` explicitly disables Flow's payload-bearing
trace logger in every repository profile. The pinned runtime exposes this setting;
the reference listener serializes workflow input/output and failure causes.
Do not enable it for real marketplace data without reviewing access, content and
retention. No upstream code or durable workflow/persistence behavior is changed.

These controls do not establish a universal redaction pipeline. Database, ORM,
scheduler, workflow dispatcher and other library logs can still contain operational
details, identifiers or throwables. Existing transaction audit metadata remains
separate. Before external collection, review all enabled categories, access,
retention, diagnostic overrides and dependency upgrades. Keep logs private and
do not assume safe HTTP problem bodies imply safe third-party logs. Refer to
[Quarkus logging configuration](https://quarkus.io/guides/logging/) when choosing
levels/handlers. Repository defaults add no exporter, collector, alert, log store
or automatic purge policy.

One INFO event per matched response increases log volume. The operator must set
storage/access/rotation and capacity budgets for the chosen runtime. Raising this
category's level suppresses its INFO events; that changes diagnostic coverage and
must be recorded. Request IDs must not become high-cardinality metric labels.

## Verification

Use Java 21 and Docker in an isolated checkout/build directory. From `services/api`:

```sh
./mvnw -B -ntp test -Dtest=RequestDiagnosticsTest,OperationsSmokeTest -Dquarkus.http.test-port=0
./mvnw -B -ntp verify -Dquarkus.http.test-port=0
```

On Windows use `mvnw.cmd`. Never point tests at a shared database. Three ordinary
HTTP scenarios capture actual log records and check:

- Successful catalog reads, a matched missing offering and invalid provider
  content retain status/correlation while headers, query/body content, token,
  subject and raw resource ID stay out of these records.
- A test-only endpoint throws a private message with a private nested cause. Its
  generic 500 and both diagnostic records correlate, without a throwable or
  either private value in the mapped error log.
- Twenty-four concurrent reads through four clients each have exactly one
  response diagnostic with a distinct generated ID. Client IDs are excluded.

`RequestDiagnosticsIT` launches the actual packaged production API, isolated
PostgreSQL 17.6 and ephemeral loopback JWKS. It checks the JSON console envelope,
one correctly correlated event for each of three status/operation cases, and
absence of synthetic private header/query/body/path/token values from that entire
process log segment. It uses no real operator/browser credentials. The synthetic
failure endpoint and log-capture fixtures are test-only and excluded from the
application artifact. Existing full workflow/restart tests exercise the engine
with payload tracing disabled; see [progress](../agent/PROGRESS.md) for results.

Further telemetry review, async/restart tracing, external collection and alert
rehearsal remain open in [#15](https://github.com/Stuaarts/Bliss/issues/15) and the
[readiness plan](READINESS.md). The deferred CI/native release gate still applies.
